# 端到端效果验证小结（2026-07）

> 目的：回答"整套优化（抽取治理 + schema v2 裁决 + 证据库）对真实需求到底有没有
> 用"。方法：多源真实资料 → 抽取 → 裁决 → LLM 成文的 A/B 对照（白酒 5 文）。
> 输出：`outputs/e2e_report_demo_A.md`（旧链路：只给原文）/
> `outputs/e2e_report_demo_B.md`（+ schema v2 裁决表，标注多源一致/单源/存疑）。
> 脚本：`scripts/e2e_report_demo.py`。

## 结论（人话版）

**1. 端到端链路跑通了——这是本次验证最重要的结果。**
从 5 篇真实白酒报道到一份 3800-4400 字的完整行业报告，全链路（检索来源→抽取→
裁决→LLM 成文→来源清单）可用，核心数字（354.9 万千升产量、3177.79 亿营收、
1225.71 亿净利、五粮液 405.29/89.54 亿等）两份报告都引用准确，未发现编造。

**2. 裁决表（我们半年工作的核心产出）的作用：有、但温和，且本次样本未充分展现。**
- B 的增量：正文中主动区分"前三季度 20 家 vs 全年 19 家"口径并说明差异、来源
  限定引用（"据新华网报道"）、结构化数据汇总表。
- **但 A 也能做到**：A 尾部同样识别了转载同源（来源 2-5 同文）与前后三季度/全年
  口径差异——LLM 从原文本身推断得出。
- 诚实归因：本样本"来源清晰、数字明确、无真实冲突"，LLM 凭原文已足够，裁决表的
  纠偏/护栏价值**没有被触发**。它真正的用武之地应是：①同一指标多值并存（跨年/
  跨口径）时防止 LLM 混用；②数字易被读错时的强制约束；③非 LLM 的结构化消费
  （EvidenceStore 查询）。

**3. 主要限制。**
单主题单次、无盲评打分；LLM 自身能力强，掩盖了抽取/裁决的部分价值；要"裁决表
提升报告可信度"的硬证据需多主题多轮 + 人工盲评，成本不低。

## 对"优化有没有用"的总回答

| 层 | 作用 | 状态 |
|---|---|---|
| 端到端可用性 | 从真实资料到完整报告 | ✅ 已验证跑通 |
| 口径纪律/抽取治理 | 让四元组语义一致（相对值 None 等），是证据库前提 | ✅ 真实且有跑分/测试佐证 |
| schema v2 裁决 | 冲突/混口径时的护栏 | 🟡 框架正确、单次样本未充分触发；价值场景待业务真实数据 |
| 证据库 | 结构化存储 | ✅ 可用，消费方待业务接入 |
| LLM 报告质量 | 不属本阶段优化对象 | — |

**建议**：这是合理的收尾点。裁决层的最终价值判定，不应靠我再造测试，而应靠
**真实业务接入后**（报告生成调用裁决表 / 证据库查询）的反馈——那才是它的考场。
